## Доказательства

Read-only просмотр Vercel Request Logs deployment
`HYLp4DvnKCMVidmx7kxmo22LqRnf` показал (время Москвы):

| Время | Запрос | Ответ |
| --- | --- | --- |
| 19:16:59.834 | GET /api/auth/patreon/start | 303 |
| 19:17:37.312 | GET /api/auth/patreon/start | 303 |
| 19:18:42.252 | GET /api/auth/patreon/callback | 303 |
| 19:18:44.992 | GET /api/auth/patreon/callback | 400 |

Второй start был отдельной HTTP-проверкой cookie-атрибутов, выполненной без
браузерной cookie-сессии. Он не должен перезаписывать браузерную state-cookie.
Тестовый заведомо невалидный callback ранее получил 400 в 19:16:45.995.

В commit 9692ac9 callback возвращает 303 только после успешного обмена кода,
получения identity, сохранения аккаунта, создания серверной сессии и аудита.
Поэтому предыдущий отчёт о провале первого callback был слишком категоричен:
серверный успешный проход зарегистрирован. Это ещё не доказывает сохранение
session-cookie браузером или наличие разрешённого tier у аккаунта.

Наблюдавшаяся пользователем ошибка `expired_or_reused_state` относится к
последующему запросу. Последовательность согласуется с повтором уже использованного
callback через 2,740 секунды. Инициатор повтора (перезагрузка, повторная навигация,
браузерный инструмент и т. п.) не установлен. Query-параметры запросов между
собой не сравнивались, поэтому совпадение state двух запросов не доказано журналом.
Нет оснований увеличивать TTL, отключать проверку cookie или разрешать повторное
потребление state. Секреты, state, authorization code и cookie в отчёт не включены.

## Жизненный цикл

1. Start генерирует 32 случайных байта (43 символа base64url).
2. В БД записываются SHA-256 и expires_at; сырой state хранится в HttpOnly-cookie
   и передаётся Patreon. Cookie: Secure, SameSite=Lax, Path=/, префикс __Host-.
3. Cookie и запись имеют общий TTL 600 секунд.
4. Callback сверяет cookie и параметр state до обращения к RPC.
5. RPC атомарно помечает только ещё не использованную и не истёкшую запись.
6. Только затем обменивается код и создаётся сессия. Ошибка после шага 5 не
   возвращает state в доступное состояние: пользователь начинает новый вход.
7. При успехе браузеру отправляется session-cookie, state-cookie удаляется.
8. Повтор со старой cookie отклоняется RPC; повтор после удаления cookie
   отклоняется ещё до RPC. Это ожидаемая защита, а не ошибка хранения state.

## Подготовленное исправление

Ранее отклонённый callback показывал сырой JSON на URL с code/state, даже если
предыдущий запрос уже создал сессию. Теперь эти отклонения переводят на фиксированный
`/early-access?auth=restart#supporters`, без параметров провайдера.

Это только навигация, не успешная авторизация: status API самостоятельно проверяет
существующую сессию и живую подписку. Без сессии отображается предложение начать
новый вход. Повтор не обменивает код, не создаёт и не продлевает сессию, не меняет
права; cookie существующей сессии и более новой попытки входа сохраняются.
Ошибки инфраструктуры по-прежнему закрывают доступ с 503. Диагностика отказа
пишет только фиксированное сообщение и код причины, без request URL и токенов.

SQL и существующая одноразовая RPC-функция не меняются. Контракт невалидного
callback меняется: после отдельной публикации ожидается 303 на безопасную
страницу вместо прежнего JSON 400. При выключенном OAuth по-прежнему 503.
